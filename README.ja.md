**AIポン出し資料（AI SLOP）を、構造的に作れなくするエージェントスキル。**
資料が失敗する原因は1つだけです。本文が、言いたいことより先に生成されること。このスキルはその順序を固定し、最後に**採点まで**します。

## 問題

AI生成資料に埋もれる管理者たちの間で回っている、差し戻しの基準があります。当てはまったら即、作り直し：

1. 直しが**10箇所以上**必要
2. 作った本人が中身を**説明できない**
3. **方向性がズレている**

SLOPへのフィードバック合戦は、双方の時間の無駄です。対策は「もっときれいな文章を書かせる工夫」ではなく、**要点のない資料が完成しない手順**です。

## 大原則

資料には**パンチラインが1つだけ**あります。読み手が持ち帰るべき一文です。これは絶対に外しません。

**細かいことは全部「補足」へ。** 注意書き、背景、データ表、例外は、明確に印をつけた補足に置きます。本文に残るのは、パンチラインを通すのに必要なものだけです。

## 手順

0. **パンチラインの関門**：一文を先に合意する。書けなければ資料はまだ早い。箇条書きで整理し、それも無理なら認識合わせの会議に戻る
1. **箇条書きが先、本文は最後**：決めたいこと・結論・最強の根拠（出典つき）・対象外を箇条書きで承認してから書く
2. **構成**：全章がパンチラインのために存在すること。そうでないものは降格テストで補足へ
3. **本文**：結論先行。パンチラインはタイトルか1行目に
4. **3つの関門**：説明できるか／直し10箇所テスト／方向性（上の差し戻し基準を自分に適用）
5. **採点つき読み手ループ**：合成読み手＋SSR採点（下記）

## 採点つき読み手ループ（SSR）

[ssr-lab](https://github.com/nomuman/ssr-lab) から借りた仕組みです。「この資料は良いか」を感覚で聞くのではなく、想定読み手のペルソナを3〜5人用意し、本文だけを読ませて、**要点の言い換え**と**感想**を自由記述で書かせます。採点スクリプトが測るのは：

- **要点の再現度（recall）**：読み手の言い換えとパンチラインの近さ。要点が届いたか
- **納得度（conviction）**：感想文をSSR（文章→5段階の埋め込み採点）で「承認アンカー」と比べたスコア

合格ライン：納得度の平均3.8以上、再現度の平均0.70以上、最低0.55以上。不合格なら、文章ではなく**構成と箇条書きを直して**再実行。最大3周まで。

このリポジトリ自身のサンプルで実際に回した結果（読み手4人ずつ）：

| 資料 | 再現度（平均） | 納得度（平均） | 判定 |
| --- | --- | --- | --- |
| 背景から始める版（`examples/sample-doc-bad.md`） | 0.583 | 2.19 | 作り直し |
| パンチライン先行版（`examples/sample-doc-good.md`） | 0.839 | 3.92 | 合格 |

良い方の資料でも、財務担当の読み手が一番低かった（3.14、「承認はできるが次回は金額を出して」）のが分かります。こういう信号を拾うためのループです。

## インストール

```
npx skills add nomuman/punchline-first
```

または `skills/punchline-first/` を使っているエージェントのスキルフォルダへコピー（Claude Code、Codex、Cursorなどスキル対応エージェント）。採点はローカルの埋め込みモデルで動くため、APIキーは不要で、資料が外部に出ることもありません。

## 自分の資料を採点する

```
# 1. reactions.json を書く（パンチライン＋読み手の言い換えと感想）
# 2. 採点する
uv run --with fastembed --with numpy \
  python skills/punchline-first/scripts/score_document.py \
  examples/reactions-good.json --lang ja
```

アンカーは日本語・英語つきで、資料の役割に合わせた2系統あります。決裁資料向けの `approval_*`（既定）と、説明資料向けの `understanding_*`（`--anchors understanding`）です。

## 設計メモ — 人気スキルから借りたこと

- **段階式の手順と読み手テスト**：Anthropic公式 `doc-coauthoring`（文脈集め→構成→読み手テスト）。読み手テストを感覚ではなく**採点式**に変えた
- **落ちることのある採点表**：`stop-slop` の採点の発想。3つの関門とSSRの合格ラインは、雰囲気ではなく合否で判定する
- **アンチパターンの名前つきリスト**：`humanizer` のパターン方式。SLOPの兆候を列挙して、エージェントが照合できるようにした
- **作る前に設計を固める**：`superpowers`（brainstorming / writing-plans）の思想
- **AIデフォルトの見た目を禁止するデザイン関門**：`frontend-slides`（スター約3.3万、AIっぽい見た目を避けるスタイル集）、`hallmark`（約4.7万、クリーム背景＋見出し上の小ラベル＋カード並べを「AIの癖」として名指し）、Anthropic公式 `frontend-design`（題材自身の世界から方向を決める。テラコッタ色のアクセント自体が癖だと自覚している）。スライドでも同じ考え方を適用し、題材から設計を宣言し、デフォルトを禁止リスト化し、「名前を入れ替えても成立するか」の納品チェックを入れた
- **スライド内容のチェック**（0.4.0）：タイトルとグラフの一致、同じことを3回言わない、資料の枠組みの再利用、同階層は文法の形をそろえる。@fujikururi「スライドの『AIっぽさ』図解」（https://x.com/fujikururi/status/2124647602448982268）から。同じ出典の見た目側のチェックは相方スキル design-urawaza の Part 3 にある
- **管理者の差し戻し基準**：AI資料のレビューで回っている「直し10箇所／説明できない／方向性ズレ」を、作る側の自己チェックに転用した

## リポジトリ構成

```
skills/punchline-first/
  SKILL.md          手順そのもの（スキル本体）
  scripts/          score_document.py（SSR読み手ループ採点）
  anchors/          承認アンカー（日本語・英語）
  assets/           Before/Afterの実例
examples/           サンプル資料＋読み手の反応＋採点結果
tests/              データとアンカーの検証
```

## 限界

- 合成読み手は簡易テストです。重要な資料では、本物の読み手の代わりにはなりません
- SSRのスコアは両端で圧縮されます。合格ラインは絶対評価ではなく、「構造に問題がある」という相対的な信号です
- パンチラインそのものは、この手順では生まれません。関門で詰まったら「まず話そう」が正直な出力で、スキルにもそう書いてあります
